# 事件 Events

## 文档用途

本页定义事件系统在战役中的作用、事件的基本结构、触发时机，以及判定和成长应遵循的写法。具体事件案例请放在[[内容设计案例/事件|内容设计案例]]或灵感库中，不在本页堆叠。

## 事件在游戏循环中的位置

事件是连接探索、营地、成长和叙事的主通道。它们负责：

- 为狩猎和营地提供变化与风险；
- 把角色成长绑定到具体经历；
- 让世界观、Boss、营地命运通过可交互内容落地；
- 给玩家提供长期记忆点，而不是只做资源结算。

一个[[术语词典/事件|事件]]可以触发后续子事件，因此事件链可以像树状结构那样逐步展开。

## 事件的基本结构

无论事件类型如何，都建议明确写出以下信息：

1. 触发条件：何时、由谁、在什么上下文触发。
2. 叙事描述：玩家先看到什么。
3. 玩家输入：是否需要选择对象、选项或支付代价。
4. 判定规则：使用什么属性、什么阈值、是否允许重投。
5. 结果与后续：立即效果、状态变化、是否挂接子事件。

## 事件类型

### 1. 抉择事件

玩家需要在多个选项中选择一个，再进行对应判定或直接结算。

每个抉择选项应当包含：

- 选项描述：玩家在做什么。
- 判定规则：使用哪个属性、目标值是什么。
- 结果展示方式：哪些信息先展示，哪些信息判定后公开。
- 结算结果：数值变化、状态变化、物品变化、后续事件。

推荐的展示原则：

- 选项描述必须和结果逻辑相关，避免“表面动作和真实风险毫无联系”。
- 失败后果可以被隐藏细节，但不能让玩家觉得是纯作者陷阱。

不推荐写法：

“你踩到液体，判定结果可能是水或血。”

推荐写法：

“你尝试站稳，成功则脱险，失败则滑落并受伤。”

### 2. 叙事事件

偏主线、世界观、Boss或战役节点的高投入事件。它们可以没有选项，但仍应保留清晰的触发条件和结果。

设计重点：

- 叙事上要承担情绪推进或信息揭示；
- 美术投入高于普通事件；
- 即使技术上与抉择事件共用模板，文档中也应标明它是叙事事件，方便内容规划。

### 3. 战斗事件

战斗事件会把玩家引入[[设计文档/决战阶段 Showdown Phase/战斗系统 Combat System/战斗系统 Combat system (索引)|战斗系统]]。

- 普通战斗：用于小规模遭遇、教学战或资源守卫。
- Boss战：用于阶段高潮或关键挑战，通常在战后直接推动战役状态变化。

## 触发时机

### 狩猎阶段事件

狩猎过程中会遭遇多次事件。它们可以：

- 指定某个猎人为触发对象；
- 修改地图或资源点状态；
- 给予人口、物资、状态或后续伏笔。

### 营地阶段事件

营地事件负责推动战役长期进展。狩猎结束后，通常抽取1张主线卡和1张随机事件卡。

- 随机事件：资源变化、人口变化、角色强化/削弱、营地风险。
- 主线事件：推进重要剧情，并可能把新事件挂到[[设计文档/营地阶段 Settlement Phase/Timeline|时间线]]上。

### 战斗中事件

战斗中事件一般与当前Boss强相关，用来做机制转折、剧情插入或奖励战斗专属能力。

## 判定与成长规则

### 推荐模式：判定属性和成长属性一致

优先让“使用什么能力解决问题”与“因此获得什么成长”保持一致。

例子：

- 用知识判定破解遗迹，成功后知识+1。
- 用胆识判定直面怪物，成功后胆识+1。

这会强化角色成长的叙事可信度，也更利于玩家理解 build 方向。

### 允许例外：属性与奖励不一致

并非所有事件都必须“测什么长什么”。如果奖励是装备、人口、资源、特性或后续剧情，只要叙事逻辑成立即可。

### 门槛选项

部分选项可以先检查一个属性阈值，再用另一属性进行判定。

例子：

- 需要知识 >= 3 才能看懂壁画；
- 看懂后，仍要用胆识判定自己是否敢执行壁画中的仪式。

这种设计适合表现“知道”和“敢做”是两回事。

## 写作约束

- 选项描述、判定逻辑、结果后果必须互相呼应。
- 尽量先说明玩家看见什么，再说明系统怎么结算。
- 先写清触发条件和效果，再补文案风格与美术需求。
- 未定项统一放在文末的待定区，不要夹在核心规则中间。
